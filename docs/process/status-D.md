## Decisions worth knowing

**daily-js comes off `window.Daily`.** `main.tsx` imports the pinned npm package (`0.92.2`, the
version research 07 verified) and assigns it to the global; `useDailyCall` reads it from there.
No CDN. This keeps the hook free of the SDK at test time — a fake global is the whole test
harness — and it is why the mock can drive the real hook rather than a parallel code path.

**Mock mode reuses the real everything.** `?mock=1` installs a fake `Daily` and a fake
`/api/sessions`, then replays `src/mock/script.ts` on a timer through the genuine
`app-message` path. The parser, the reducer, the thinking timer and every component run exactly
as they do on a real call. If the contract drifts, mock mode breaks the same way the real bot
would. The whole script is ~30 s.

Its four card snapshots come from `src/mock/snapshots.json`, which Session A generates from real
domain fixtures with `scripts/dump_mock_snapshots.py`; the script holds only the RTVI text cues
around them. The journey therefore cannot show a number the engine could not produce, and the
browser tests assert the engine's own figures rather than strings written for a test.

**A fourth `thinking` action.** RTVI gives `user-started-speaking` but no matching stop, so the
pill could only ever show three of its four states. The hook starts a 1.2 s timer when the user
begins talking and cancels it if the bot starts speaking; the reducer just handles a plain
`thinking` action, so it stays trivially testable.

**`parseIncoming` rejects rather than repairs.** Card text is LLM-generated. Every field is
checked, an unknown card id / phase / status fails the whole snapshot, and RTVI traffic outside
the four types we consume returns `null`.

## Known limitations

**A session response without `session_id` yields a call that cannot be cancelled.**
`SessionStartResponse` declares `room_url`, `token` and `session_id` as required, but
`isSessionResponse` validates only the first two. A response missing `session_id` therefore starts
a working call, and the F8 cleanup (`DELETE /api/sessions/{session_id}`) silently does nothing if
that call then fails before `joined` — leaving the server slot committed until it times out, the
exact symptom F8 fixed.

The trade is deliberate and agreed with the orchestrator: the id is needed only for cleanup, so a
working call beats a refused one. It is pinned by a test ("skips the cancel when the server did not
name the session"). Making it strict is a one-line change to `isSessionResponse` plus that test.
The condition cannot arise while the backend honours the contract.

**The mock is the only journey ever driven end to end.** The card snapshots are real
`build_cards` output, but no live LLM has filled these fields in sequence, and no real Daily
`app-message` has ever reached the parser. Row text or note lengths from an actual call may still
exceed what the layout has met.

**Two implemented behaviours are no longer exercised by the review journey.** The generated
snapshots contain no `"not known"` row and no `["+N more", "", ""]` trim marker, so the parked
chip and the muted trim line are covered by vitest only, not by `?mock=1` or the e2e walk.

**The 4 KB trim path is only simulated.** `["+N more", "", ""]` and the truncation sentence are
rendered from hand-written fixtures; no snapshot produced by a real `build_cards` at the size
limit has been through the UI.

# Addendum · the sixteen POST /api/sessions from one page

Reported from the owner's first live call: one `POST /api/sessions` 201 at 23:17:49, the browser
joined at 23:17:54, then fifteen more POSTs from the same client port answered 409, ending only
when the user reloaded and started fresh.

I reproduced it with a fake fetch that answers 201 then 409
(`frontend/src/call/restart.test.ts`). **Six tests failed on the old code.** Three defects, all
fixed:

### 1. The guard could not see a start that was still in flight

`start()` refused a second call by checking `callRef.current` — but that ref is only assigned
*after* `await fetch(...)` returns. Every gesture landing inside that window passed the guard.
Three `start()` calls in one tick produced **three** POSTs and three call objects.

Fixed with `startingRef`, set synchronously before anything is awaited and cleared in a `finally`
that covers every exit path. Three calls in one tick now produce exactly one POST.

### 2. The call object was never released when a call ended on its own

This is the one that matches the log's shape, and it is the worst of the three. `stop()` tore the
call down, but `participant-left` (the bot leaving), a fatal `error`, and `camera-error` only
dispatched a message — `callRef.current` stayed set. So after any of those the call was over as
far as the UI was concerned, the user saw a "Start another call" button, and **every press was
silently swallowed by the guard.** The only escape was reloading the page, which is exactly how
the live call ended.

Those three handlers now call `release()`, which leaves and destroys the call object.

My earlier suite missed this because the only restart test went through `stop()`, the one path
that already tore down correctly.

### 3. A 409 was reported as a network failure

Any non-2xx fell into one `catch` that said "Could not reach the server." A 409 now has its own
message — **"A call is already running. End it first, then start a new one."** — and is checked
before the generic path.

### Also done

- **The Start control is disabled while connecting or live** (`aria-busy`, label changes to
  "Starting…"), and the error banner's "Try again" is disabled on the same condition. The app now
  stays on the start screen while connecting, with the button visibly disabled, instead of
  swapping in an empty board — the user can see the press was taken. `App.disabled.test.tsx`
  covers it, including three clicks producing one POST.
- **Favicon.** `frontend/public/favicon.svg` (a balance line dipping below zero and recovering —
  the shape the `Timeline` draws), declared in the head with `rel="icon"` plus an
  `alternate icon` fallback. Verified in Chromium: **the browser no longer requests
  `/favicon.ico` at all**, which is what removes the 404 — note that a direct request for
  `/favicon.ico` would still 404, because the fix is the declaration, not a new file. If the
  server should answer that path regardless, that is a backend route, not a frontend file.

### What I could not determine

The client no longer posts more than once per gesture, and the "pressable but dead" state that
best explains the repeat is gone. But **nothing in the frontend ever retried on a timer**, and
nothing I can find would produce fifteen POSTs across 41 seconds without fifteen gestures — the
spacing (~2.7 s apart) reads like a person pressing a button that appeared to do nothing, which
defect 2 made possible. If the server log shows the same pattern again after this fix, the next
place to look is the server's own retry or health-check path, not the page.

## F8 — a failed join stranded the only server session

Confirmed. `POST /api/sessions` commits the single server slot before the browser has created or
joined anything, and every failure after that 201 left it committed, so the retry the error
message invited got a 409.

`cancelSession(sessionId)` now issues `DELETE /api/sessions/{session_id}` on all three failure
points between the 201 and `joined`:

1. `globalThis.Daily` missing;
2. `createCallObject` throwing (Daily throws if an earlier object was never destroyed — this path
   did not exist before and is now handled with its own message);
3. `join()` rejecting.

It is best effort and wrapped in its own `try`: a failed cleanup must never replace the reason the
call did not start. Eight tests in `src/call/cancel.test.ts` cover each failure point, that no
DELETE is sent when the POST itself failed or when the call came up fine, that a failed DELETE
still reports the real error, and that the very next `start()` succeeds.

**One judgement call, confirmed by the orchestrator and recorded under Known limitations above:**
`isSessionResponse` requires only `room_url` and `token`, not `session_id`, so a response missing
the id starts a working call that cannot be cancelled rather than being refused. A working call
beats a refused one; a test pins the behaviour.

## A-2 — wider conflicts, and values the user does not know

  tests: four notes covering a date, a debt kind, a card minimum and an opening balance each

  frontend inspects anywhere is a trailing `" ?"` on a row *value*, and the word `unpaid` /

- **"not known" rows render parked, not pending.** A missing-card row whose third column contains

  chip used for a live question, and the missing card's `note` is rendered underneath. Three
  tests, plus the mock script now carries one so it is visible in review
  (`9-not-known-chip.png`).

# Addendum 7 · review 6, finding F3

**A late event from a finished call could tear down the call that replaced it.** Every call
object's handlers called one shared `release()`, and `release()` tore down whatever was in
`callRef` at that moment. Real Daily delivers `left-meeting` some time after the call has gone,
so: the bot leaves, the UI is told and offers "Start another call", a new object lands in
`callRef` — and then the old object's delayed `left-meeting` fires, calls `release()`, and leaves
and destroys the **new** call.

My own test double hid it. `FakeCall.leave()` emitted `left-meeting` synchronously, so the two
events could never interleave the way they do in a browser, and every restart test passed.

Three changes:

1. **`teardown(call)` takes the instance** instead of reading the ref, and only clears `callRef`
   when the call being retired is still the current one.
2. **Every handler is bound to its own call object** and returns early unless
   `callRef.current === call`. A straggler from a finished session now reaches neither the
   reducer nor the teardown.
3. **`start()` waits on a pending teardown** (`teardownRef`) before creating anything, so two
   Daily objects never coexist — the factory throws on a second instance, and the server keeps
   one session.

The fake gained `emitsLeftOnLeave` and a `destroyGate` so a test can hold `destroy()` open and
reproduce the real ordering; the four new tests in `src/call/lateEvents.test.ts` all failed
before the fix.

**Each half is mutation-checked independently.** Replacing `isCurrent()` with `() => true` fails
two of them; dropping the `await` on the pending teardown fails the third.

**One regression I introduced and fixed.** Nulling the ref before `leave()` means the End button's
own `left-meeting` is now correctly ignored as a straggler, so `stop()` stopped telling the reducer
anything. `stop()` now dispatches `left` itself — pressing End *is* the decision, and waiting for
Daily to echo it back was the weaker design to begin with.

the server. `App` refuses to post an invalid number and says what it wants instead; the number is
remembered only when a call actually starts, not as it is typed.

Granted as request **F-1**, in `call/`: `start` takes the phone, the POST carries `{phone}`, and a
422 gets its own sentence — matched on the status code alone, so C's detail string is free to
change. The 69 existing `start()` call sites took the argument mechanically; the four `App` test
files seed `localStorage` in `beforeEach`, which is the returning-caller state they were already
about.

## Step 2 · the judge's verdict on screen

`verdict/useVerdict.ts` polls `GET /api/sessions/{id}/verdict` every two seconds for a minute from
the moment the call ends. A 202, a network error, and a body that is not a verdict are all "not
yet"; after a minute it says the review did not come back rather than reviewing for ever. The
result is keyed to the `(session, ended)` pair, so the previous call's verdict cannot appear under
the next one, and no state is set synchronously inside the effect.

`components/VerdictPanel.tsx` prints the deterministic rules with the sentence that broke each one,
the intent criteria with all three outcomes written out as words and the turn quoted, the summary
score, the judge model, and the Langfuse trace link **only** when `trace_url` is there. A failed
verdict says so in a line; an empty panel would read as a pass.

Granted as request **F-2**, in `mock/`: `?mock=1` answered any URL containing `/api/sessions` with
the session-start body, which would have handed the poll a room URL to read as a verdict. It now
answers only the POST that starts a call and the DELETE that cancels one; everything else reaches
the real fetch, where the browser test's `page.route` can mock it.

## Step 3 so far

The `carried` status word ("from last call", styled with `provisional` rather than `warn` — nothing
on the card is wrong, it is last call's figure waiting to be confirmed), a test over A's `returning`

# Agent redesign · the none row and the low point on screen

## A kind the person has none of

`build_cards` now sends the card with one `["None", "", ""]` row instead of omitting it, because
"no loans" and "nobody asked about loans" looked identical when the card was simply absent.
`CardRows` renders that as a single serif-italic answer with no amount cell beside it — a blank
amount column reads as a figure still to come. The predicate is `isNoneRow` in
`protocol/markers.ts`, requested rather than written on my side so the wire vocabulary keeps one
home; it matches a "None" label with an empty value, so a real item someone calls "None" with a
figure against it is not swallowed. Five tests, one of them that exact case.

## Why the month gets that low

`components/LowPointWorking.tsx` prints the derivation under the figure and the chart: the
starting balance, every movement before the low day with its own date, the low itself, what
arrives after, and where the month closes. A spread item reads "to 30 Sep" rather than as a
payment on that day, because that is what `spread` means.

**The totals are added up in the page from the lines shown, not restated from the message.** The
contract guarantees `opening + sum(before) === b` and `b + sum(after) === closing`; the panel
computes both and renders what it computed. When the two disagree — a truncated derivation, or a
bug upstream — it says so and names the figure the plan actually used, rather than printing a
number that looks like arithmetic and is not. That case has its own test, and the browser test
asserts the agreement flag on the real snapshot rather than comparing strings.

engine does not produce, and a low point of −1,800 on 5 Oct where the engine says 0 on 25 Sep.
