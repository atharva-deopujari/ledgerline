# Orchestration: four parallel implementation sessions

Read this first, then your own brief (`docs/process/session-<letter>.md`). The orchestrator session (a
separate Claude session, not you) verifies and integrates. You implement your slice only.

## Rules for every session

1. **Never commit, never push, never `git add`.** The owner reviews every file by hand. Leave the working tree
   dirty. Do not run `git stash`, `git checkout`, or anything that touches other people's files.
2. **Touch only files you own** (table below). If you need a change in someone else's file, write the request in
   `docs/process/requests.md` under your session letter and stop working on that item. Do not edit their file.
3. **Do not edit `pyproject.toml` or `uv.lock`.** Every dependency you need is already there. If one is missing,
   write it in `docs/process/requests.md`.
4. **Contracts are fixed.** `ledgerline/domain/models.py`, the signatures in `state.py`, `engine.py`, `policy.py`,
   `cards.py`, `agent/tools.py`, `agent/prompt.py`, and `frontend/src/protocol/types.ts` define the shared
   interfaces. Fill in bodies; do not rename or retype anything public. Adding an optional field with a default is
   allowed if you note it in `requests.md`.
5. **TDD, strictly.** For each unit of behaviour: write the failing test first, run it and watch it fail for the
   right reason, write the minimum code to pass, run again, then refactor. Commit nothing. Keep tests fast and
   offline; paid or networked tests carry the `llm`, `voice` or `e2e` marker so plain `uv run pytest` never
   runs them.
6. **Run only your own tests:** `uv run pytest tests/<your area>`. Other areas may be mid-edit and red.
7. **Verify Pipecat and vendor APIs before using them.** Use the `pipecat-context-hub` MCP (`search-api`,
   `check-deprecation`, `get-code-snippet`) and context7. Every pre-1.3 tutorial is wrong about class names.
   `docs/research/00-index.md` lists the renames.
8. **Read before writing:** `docs/architecture/02-hld.md` (the design), `03-folder-structure.md` (where things go),
   and the research reports named in your brief. Do not re-research what is already verified.
9. **No Claude attribution anywhere.** No co-author lines, no session links, no "generated by" comments.
10. **Protect your context: delegate bounded work to subagents.** Anything that does not need your full
    history goes to an `Agent` call on Opus: mechanical test moves, greps and censuses, running a paid
    simulation matrix and summarising the table, a headless measurement loop, reading a long log for one
    fact, generating fixtures. Give the subagent the file paths and the exact question, forbid nested
    agents, cap it at about 40 tool calls, and have it write its report file early and append. You keep
    judgement, design and anything touching a contract. A session at 25 percent context stops and writes a
    handover section instead of starting new work.
11. **When done**, write `docs/process/status-<letter>.md`: what is implemented, test count and result, anything
    left, anything you had to assume. Then stop.

## Reporting to the orchestrator

The orchestrator is another Claude Code session on this machine named **`ledgerline-orchestrator`**. You can
message it directly with the `SendMessage` tool (`to: "ledgerline-orchestrator"`); run `ListAgents` first if you
want to confirm it is present. Message it, in one or two sentences each time:

- when you start ("Session A started, working on policy.py");
- when you write anything in `docs/process/requests.md`;
- when you are blocked for more than a few minutes on something outside your files;
- when you finish and have written `docs/process/status-<letter>.md`.

Do not wait for a reply to keep working unless you are blocked. The orchestrator may message you with
answers, contract clarifications or a request to re-run tests; treat those as instructions from the owner. Do
not message other worker sessions directly; everything goes through the orchestrator so one place holds the
whole picture.

## Shared facts you will need

- Python 3.11, `uv run` for everything. `uv run pytest tests/<area>`; `uv run ruff check .`; `uv run lint-imports`.
- Pipecat **1.9.0**. `PipelineWorker` not `PipelineTask`; `WorkerRunner` not `PipelineRunner`; `LLMContext` +
  `LLMContextAggregatorPair`; VAD goes on `LLMUserAggregatorParams`, not the transport; the system prompt is
  `Settings(system_instruction=...)` updated with `LLMUpdateSettingsFrame`; `OutputTransportMessageUrgentFrame` for
  cards; `enable_rtvi=True` is the default. Full list: `docs/research/00-index.md`, "Facts that changed earlier
  assumptions".
- Model id is exactly `gpt-5.6-luna`. Reasoning effort must be `none`. Never set temperature.
- Money is `Decimal` quantised to `0.01`. Dates are `datetime.date`. "Today" in tests is `date(2026, 9, 11)`,
  horizon 30 days inclusive, so the window is 2026-09-11 to 2026-10-10.
- Cards message must serialise under 4096 bytes.
- The LLM never computes. Every number it speaks came back in a tool result string.

## Definition of done for the whole build

`docker compose up --build` then `http://localhost:7860`: a user starts a call, states salary, two debts, rent,
forgets electricity and is asked, gives a conflicting number and is asked which is right, corrects salary and
every card updates, hears a plan with a shortfall and two actions, restates them, sees the final plan card,
ends the call. That is the journey every session is building one slice of.
